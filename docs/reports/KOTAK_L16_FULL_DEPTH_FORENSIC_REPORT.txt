5. L16 PROTOCOL / MESSAGE SEMANTICS  [CODE VERIFIED + LIVE VERIFIED]
--------------------------------------------------------------------------------
protocol.py:51-52 header: message_length u16, message_code u16, exchange_id i8,
            level u8, auction_flag u8, seq_no u8, bitmask_length u8.
protocol.py:158 routing: levels {2, 4, 8, 16} all decode to SFeedScrip via
            _decode_market_picture (message_code 7208 = MSG_MARKET_PICTURE,
            protocol.py:38). Level 16 is NOT a separate message_code.
protocol.py:282-377 _decode_market_picture:
    * Token + 23 market scalars unpacked from the fixed 135-byte body (@9..@144).
    * buy_depth_count and sell_depth_count are READ FROM THE WIRE (body u32s).
    * Touch line (level 4) forces buy_n=sell_n=1 (hard-coded).
    * ALL OTHER LEVELS (incl. 16) use buy_depth_count/sell_depth_count verbatim.
    * Depth rows are read after byte 144 as consecutive 16-byte rows
      (qty i64, price i32, orders i32 -> price/divider).
    * If the packet ends before the advertised rows, decoding stops (partial
      book is possible; broken rows are NOT synthesised).
CONCLUSION: the SDK does NOT guarantee "16+16" for level 16. The number of
rows is whatever buy_depth_count/sell_depth_count say in each packet. Level
16 in the SDK only names the subscription tier; the actual book size is a
runtime property of the feed. URL-level doc value "FULL_DEPTH=16" is the
level tag, not a promised row count.  [DOCUMENTED vs CODE vs LIVE separated]
Discarded wire fields (decoded but never exposed on any SFeed model):
    message_length, message_code (routing only), seq_no, bitmask_length,
    _indicative_close, _trading_status.     [CODE VERIFIED; also see section 12]
